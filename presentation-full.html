Part 2 · Infrastructure as artifactsOpenTofu / Terraform: one module per layer

  • One layer per concern, each its own state: a DNS change never re-plans the network.
  • Each layer is a module with inputs, outputs and a version; modules live in a module registry.
  • Outputs are the IDs (VPC id, cluster name, role ARNs) that the company's repo will reference later (slide 12).
A layer is an InnerSource artifact: published, versioned, pinned, contributed to.

1:15 · OpenTofu: infrastructure in layers. · Oscar

Infrastructure as code starts with OpenTofu, or Terraform if you prefer the original name. The useful habit is to build in layers: (→ step 1: the five layers stack up from the bottom) networking at the bottom, identity, compute, the Kubernetes clusters, and at the top the entry points: load balancers, DNS, certificates. Each layer is a module with a version, (→ step 2: the arrows up the left side) and each layer's outputs are the inputs of the next. (→ step 3: the three bullets and the callout) Those outputs, the VPC id, the cluster name, the role ARNs, are the IDs you will see again when we get to the company's repo.

Part 3 · GitOpsGitOps in one picture: merged means deployed

from artifacts to a whole platform
  • Declarative — the repo describes what, never how.
  • Versioned and immutable — every state has a commit; rollback is git revert.
  • Pulled automatically — the controller pulls; nobody pushes to the cluster.
  • Continuously reconciled — drift is corrected, not just reported.
“Merged” means “deployed”.

1:15 · GitOps in one picture. · Oscar

GitOps is a loop. (→ step 0: the repository enters with the slide) The repository holds the desired state. (→ 1: controller, cluster and reconcile enter and the ring is traced) A controller, Argo CD or Flux, runs inside the cluster, compares what is with what should be, and converges. (→ 2: the dot runs the loop once, then the four principles) Nobody runs kubectl apply; nobody pushes to production. (→ 3: the dashed PR arrow and the callout) (context: a merged pull request changes the desired state; the controller does the rest.) You change production by merging a pull request. And that one sentence is why InnerSource applies: if a merged PR is how infrastructure changes, then who may open one, who may approve it and what checks it must pass is, by definition, the governance.

⚠ The four principles are the OpenGitOps v1.0 wording (Declarative; Versioned and immutable; Pulled automatically; Continuously reconciled): verify the exact phrasing. · Name both engines, Argo CD and Flux, on every GitOps slide; the examples in 10–12 are written with Argo CD (decision 26 Oct 2026; swap to Flux if Oscar's teams run Flux). · If 07 is cut, open with: “Single components already fit InnerSource. 1:30 · Policy-as-code guardrails. · Juan David

Approval boards exist because the rules were never written down anywhere a machine could read them. (→ 1: the Policy as code column) Write them as policies, put them in a repository owned by the security and risk teams, and three things happen: (→ 2: the three tiles, where the rules run, left to right) every PR is checked before a human reads it; the cluster refuses what the policy forbids, even if the PR slipped; and the board's job changes. (→ 3: the line under the tiles) It no longer reviews every change; it reviews the rules, and an exception is a PR with evidence attached. Governance doesn't get weaker when everyone can contribute. It gets written down. (the last two sentences are the quote of slide 22: said here once, shown there)

Part 6 · The roadmapWhat breaks, and what to design against

the repo side
  • Forking the platform instead of overlaying → every fork is a company that stopped contributing
  • Unpinned refs (ref=main) → a base change deploys everywhere at once; pin and bump
  • Secrets in Git → an external secrets operator; Git holds references, never values
  • Policies without tests → a policy is code; it gets unit tests and a PR
the people side
  • The board comes back as a mandatory reviewer on every PR → the board reviews rules, CODEOWNERS reviews changes
  • No Trusted Committers from subsidiaries → then it is a central team, not InnerSource
  • No preview for platform PRs → reviewers approve blind; give them a diff and an environment
  • Agents with cluster credentials → agents open PRs; only the GitOps controller deploys

1:00 · What breaks. · Juan David

A few things we have seen break, or designed against. (→ 1: the repo side) Forks: the moment a company forks the platform, it has stopped contributing. Unpinned references: a change in the base should never deploy everywhere by surprise. (→ 2: the people side) And the people side: the approval board quietly returning as a required reviewer on every pull request, or a shared repo where every Trusted Committer works for the holding and none for a subsidiary. That last one is the difference between InnerSource and a central team.
